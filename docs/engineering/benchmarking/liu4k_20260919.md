Point-in-time report. Dataset: Muñoz-Salinas, R., *Liu4K dataset employed for Aruco_Nano paper*,
Zenodo, 2026, [doi:10.5281/zenodo.18667018](https://doi.org/10.5281/zenodo.18667018), licensed
[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/legalcode). The record's free-text
`copyright` field also reads "CC0 License"; CC BY 4.0 attribution is applied regardless. The data is
read unmodified; nothing is redistributed. See
[Real-World Evaluation (Liu4K)](../benchmarking.md#real-world-evaluation-liu4k) for how to run it.

> **Latency correction (measured 2026-09-20).** The first version of this report labelled its Locus
> rows by the `Detector(threads=)` argument. That argument is **dead** — it is stored and never read
> (`detector.rs`), so it cannot change the thread count — and `RAYON_NUM_THREADS` was left unset, so
> the global Rayon pool used all 8 vCPUs. Every row labelled "1 thread" in that version was in fact an
> 8-thread run, and the "8 threads" rows were the same 8-thread configuration measured twice. All
> latency numbers and every thread-related statement below have been re-measured with the thread count
> set **only** through `RAYON_NUM_THREADS`, on an otherwise idle machine. **Accuracy is unaffected:**
> every TP/FP/FN tally re-ran bit-identical to the published values at both thread counts, so all
> recall, precision and F1 figures in this report are the original ones.

## Scoring (mirrors aruco_nano `testperf.cpp`)

For every detection, in output order: it is a **TP** if the first not-yet-matched GT marker with the
same id has a centre distance `<= 10 px`; otherwise it is a **FP**. **FN = GT - TP**. Centres are the
mean of the 4 corners. The 10 px radius is a Liu4K-specific constant
(`LIU4K_MATCH_THRESHOLD_PX` in `tools/bench/liu4k.py`); the repo-wide
`MATCH_DISTANCE_THRESHOLD_PX` used by other datasets is unchanged. An id-agnostic *quad* variant uses
the same rule without the id condition, over accepted plus decoder-rejected quads (its precision is
not meaningful: on the `standard` profile with sharpening off it reports 182k candidate FPs, because
every funnel-passed noise quad counts).

Dataset: 924 images (about 3300x4900), 9022 GT markers, ids 0-249 (`ARUCO_MIP_36h12`, 250 codes).

## Harness sanity checks (ruled out first)

- GT overlays on several images line up with the physical markers; decoded detections agree with GT
  ids and lie within 1 px of the GT centre.
- No EXIF orientation tag on the images checked; image sizes vary per image and GT is in each image's
  own pixel frame.
- The GT corner **winding is opposite** to Locus/OpenCV (counter-clockwise vs clockwise on screen,
  corner 0 shared, order 0,3,2,1). It does not affect the centre-based scorer; any future corner-error
  metric must map it.
- The +0.5 pixel convention is irrelevant at a 10 px tolerance.

## Why recall is low: quad stage, not decode stage

Locus `standard`, 9022 GT: **2591 decoded (28.7 %)**, 42 quads formed but rejected by decode, **0 wrong
ids**, and **6389 (70.8 %) with no quad at all** within 10 px. Decode is not the bottleneck; quad
formation is. With the best config below, 4770 decoded, 113 rejected, 4139 with no quad.

Dependence on marker properties (best config, decoded %):

| Marker edge (px) | <20 | 20-45 | 45-100 | 100-250 | >=250 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| Locus (no sharpen, relaxed) | 67 | 68 | 58 | 51 | 41 |
| aruco_nano | 50 | 70 | 66 | 68 | 68 |
| OpenCV 4.10 | 0 | 14 | 70 | 66 | 61 |

| Mean marker intensity | <30 | 30-60 | 60-100 |
| :--- | ---: | ---: | ---: |
| Locus | 32 | 58 | 87 |
| aruco_nano | 52 | 72 | 90 |
| OpenCV 4.10 | 42 | 66 | 75 |

Recall does not depend on `rot` (52.4-53.2 % across the four values) or id (51.8-53.7 %).
The dataset is a composite: markers are alpha-blended into photos, many are dark (about 40 % of GT
markers have mean intensity below 30/255) and low contrast, and there are many distractor squares.
Recall rises with sharpness (Laplacian variance quintiles: 37 % to 78 %). Locus is better than both
references on tiny markers (<20 px; OpenCV finds none) and matches aruco_nano at 20-45 px, but loses on
**large** markers (>=100 px) and on **dark** ones.

The `tools/bench/tune` harness is tied to the hub datasets, strata and pose metrics, so this sweep used
a scratch driver that builds `DetectorConfig` objects from the shipped profiles; the shipped JSON
profiles were not edited.

External preprocessing (Locus config: sharpening off): Gaussian blur sigma 1 gives 50.62 % (+0.9 pp)
but sigma 2 and 3 lose recall (46.95 %, 41.58 %). An area-averaged 2x downscale (`cv2.INTER_AREA`)
gives 48.05 % at roughly a quarter of the latency (36.7 vs 140.4 ms at 1 thread, 22.6 vs 80.0 ms at
8). Running full-resolution plus 2x plus 4x detectors and taking the union of decoded markers reaches
55.4 % recall (FPs at most 48), a +2.5 pp gain over the best single pass. The union was never timed;
the 4x pass was not timed either, so no latency figure is quoted for it here.

### Thread scaling (1 -> 8, same run)

| Config | 1 thread | 8 threads | Speedup |
| :--- | ---: | ---: | ---: |
| Locus `standard` | 163.9 | 118.8 | 1.38x |
| Locus `grid` | 156.1 | 85.9 | 1.82x |
| Locus `high_accuracy` | 138.0 | 101.7 | 1.36x |
| Locus sharpening off | 140.4 | 80.0 | 1.76x |
| Locus sharpening off + relaxed gates | 169.7 | 89.4 | 1.90x |
| Locus sharpening off + 2x downscale | 36.7 | 22.6 | 1.62x |
| OpenCV 4.10 `aruco` | 333.8 | 249.7 | 1.34x |
| aruco_nano | 55.6 | 55.6 | 1.00x |

No detector on this table comes close to 8x on 8 vCPUs (4 physical cores + SMT). Locus tops out at
1.9x; `standard` and `high_accuracy` scale worst (1.36-1.38x). aruco_nano does not scale at all, and
OpenCV's aruco gains only 1.34x — its adaptive-threshold stage is not parallelised in this build
(`adaptiveThreshold` on a 4900x3300 image measures 15.0 ms at 1 thread and 15.0 ms at 8), while
`GaussianBlur` on the same image scales 4.1x, so the backend itself is working. Locus's own ceiling is
a large serial section inside `detect()`, not a missing thread knob: with eight workers available only
about two are ever busy (finding 5).

Detection overlap with the best Locus config: aruco_nano finds 1515 GT markers that Locus misses and
Locus finds 246 that aruco_nano misses; against OpenCV the numbers are 1382 and 947.

## Best configuration and Pareto

On this dataset `standard` with **`threshold.enable_sharpening=false`** is the best default: it
recovers +21 pp of recall at unchanged precision and is faster at both thread counts (140.4 vs
163.9 ms at 1 thread, 80.0 vs 118.8 ms at 8).
`bench real --dataset liu4k --family ArUcoMip36h12 --no-sharpening` reproduces it exactly
(4482 / 10 / 4540). Non-dominated points on (recall, precision, latency), at both thread counts: the
2x-downscale pipeline (36.7 / 22.6 ms, 64.9 F1, highest precision among the usable points),
sharpening-off (140.4 / 80.0 ms, 66.3 F1) and sharpening-off with relaxed gates (169.7 / 89.4 ms,
69.0 F1, lowest precision at 99.25 %). `grid` is dominated by sharpening-off (same F1, slower at both
thread counts); `standard` is dominated. `high_accuracy` is dominated at 8 threads, and at 1 thread it
is only nominally non-dominated: it is 2.4 ms faster than sharpening-off (138.0 vs 140.4) for 5 pp
less recall, and 2.4 ms is inside this harness's run-to-run noise.
Precision stays at or above 99.25 % everywhere, so recall and latency decide.
Even the best Locus config trails aruco_nano (66.9 %) and OpenCV (57.7 %) in recall on the same
scorer. On latency it beats OpenCV at both thread counts (169.7 vs 333.8 ms at 1 thread, 89.4 vs
249.7 ms at 8) and loses to aruco_nano at both (55.6 ms, which does not change with threads).

## Findings that need a decision (no detector code changed)

1. **`quad.upscale_factor > 1` returns corners in the upscaled frame.** On `004.jpg`, id 79 decodes
   with centre (3088, 3002) at factor 2 versus (1543.8, 1500.8) at factor 1 (GT 1543.4, 1500.6); a full
   run gives TP=0, FP=3238. In `detector.rs` (`detect` preprocessing) the scale from the upscale branch
   is bound to `_effective_scale` and never used, and the funnel gate is given `1.0 / config.decimation`.
   Ids decode, so only the coordinate mapping is wrong.
2. **Two config fields are inert here.** `threshold.constant` (`adaptive_threshold_constant`) has no
   reader outside config plumbing, and `threshold.gradient_threshold` gave bit-identical TP/FP/FN for
   0, 5, 20 and 40; `threshold.min_range` (0-40) and `decoder.min_contrast` (0-40) also gave identical
   results on all 924 images (they are read but never bind on this data).
3. **Sharpening default.** `standard` enables Laplacian sharpening; on this noisy, low-key data it costs
   21 pp of recall. This is a tuning question for the shipped default, not proven to be a defect;
   changing it needs the ICRA and render-tag regression suites.
4. **Large clean markers are missed on textured backgrounds.** `004.jpg` marker 229 (edge about
   310 px, crisp black border on water) yields no quad, not even a rejected one, at full resolution on
   every shipped profile and on EdLines. It is found after a 2x or 4x area downscale or a sigma-2 blur.
   A numpy emulation of the tile threshold (3x3 tiles, midpoint of min/max, range gate 10) shows the
   marker's foreground merging with water-texture speckle and its deep black interior flagged as
   low-range, which is consistent with the miss. That is a hypothesis about the Rust internals, not a
   confirmed root cause. OpenCV uses several adaptive-threshold window sizes and aruco_nano a
   contour tracer, which is one plausible reason both do better on markers of 100 px and larger.
5. **`Detector(threads=)` is dead, and real thread scaling tops out at 1.9x.** Two separate facts,
   both re-verified on 2026-09-20:
   - *The parameter does nothing.* `DetectorBuilder::with_threads` writes `config.nthreads`
     (`detector.rs:642`) and nothing ever reads it: `nthreads` appears only in its declaration
     (`config.rs:222`), its defaults and the serde copy, and there is no `rayon::ThreadPool`,
     `build_global` or `num_threads` call anywhere in `locus-core` or `locus-py`. Measured: at a fixed
     `RAYON_NUM_THREADS`, `threads=None/1/8/64` give **bit-identical ids and corners** and the same
     latency (183-193 ms at `RAYON_NUM_THREADS=1`, 132-134 ms at 8 — the spread is noise, and the two
     groups differ only by the env var). The thread count is decided solely by `RAYON_NUM_THREADS`, or
     by the core count when it is unset. `docs/reference/api.md` still describes the argument as the
     "Rayon intra-frame thread count (0 = all cores)". It must be wired (a scoped
     `ThreadPool::install` that does not allocate in the hot loop) or removed along with its docs.
     This is what invalidated the first version of this report's latency table.
   - *Scaling is Amdahl-limited, not thread-starved.* With `RAYON_NUM_THREADS` actually set, 1 -> 8
     threads buys only 1.38x on `standard` and at best 1.90x on the relaxed config, on 8 vCPUs.
     `detect()` is genuinely handed the eight workers and keeps only about two of them busy: over a
     25-image subset on `standard`, CPU time / wall time during the detection loop is **1.00 cores at
     `RAYON_NUM_THREADS=1` and 1.98 cores at 8**, while total CPU work rises 8.56 s -> 10.98 s
     (+28 % parallel overhead) for a wall drop of 8.56 s -> 5.55 s. A 1.38x speedup on 8 workers
     implies a parallel fraction of only about 0.31, i.e. roughly two thirds of a `standard` 4K frame
     is serial. Locating that serial section is a detector-internals question and is **not measured in
     this report**; a separate root-cause investigation attributes it to the connected-components
     stage (`pipeline::segmentation` / `label_components_lsl`, which contains no rayon), which would
     also mean `pipeline.md`'s "0.5 ms segmentation @720p" budget does not survive textured 4K input.
     That attribution needs its own instrumented measurement before it is treated as established.
